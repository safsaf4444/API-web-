Info

This page explains how keys work for AI and Semantic Scholar. Search is available in Guest Mode, but saving, comments, and AI require login.

Guest Mode vs Login

Guest Mode
You can search and open papers from external providers (Europe PMC, Semantic Scholar). You can’t save, comment, or use AI without logging in.
Login Required For
• Saving papers to your library
• Notes and folders
• Comment threads
• AI features (Summarize / Ask)

AI (BYOK — Bring Your Own Key)

The app does not ship with an AI key. You provide your own OpenAI API key and the backend uses it only for your requests.
What happens when I set my key?
• Your key is sent to the backend over HTTP (localhost).
• The backend stores it encrypted in the database tied to your user.
• The frontend does not store your OpenAI key in localStorage.
What uses the key?
These endpoints require login and a stored key:
• POST /ai/summarize
• POST /ai/ask
The AI only sees the paper’s title + abstract (unless you add full-text support later).
Key management endpoints
• POST /ai/set_key — store/update your key
• GET /ai/key_status — shows masked key status
• DELETE /ai/clear_key — remove your key
Security notes (local dev)
Since you run this locally, “security” is mostly about not leaking keys into the browser. For production, use HTTPS, stronger secret management, and rotate keys.

Semantic Scholar API Key

Semantic Scholar often rate-limits unauthenticated requests. Adding an API key increases reliability and reduces “429 Too Many Requests”.
Where does the Semantic Scholar key go?
The Semantic Scholar key should be configured on the backend as an environment variable. The frontend does not need to store it.
How to set it (recommended)
Set an environment variable before starting the backend (name depends on your backend code).
Common patterns are:
SEMANTIC_SCHOLAR_API_KEY=your_key_here
Then restart the backend.
How you’ll know it’s working
Searches against Semantic Scholar should stop throwing 429 errors and return results consistently.
